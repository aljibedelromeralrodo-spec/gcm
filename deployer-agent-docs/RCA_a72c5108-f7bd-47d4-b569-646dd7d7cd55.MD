# RCA — Central Mutuos: "Error enviando correo / origin returned invalid or incomplete response" (Cloudflare 502)

## Veredicto
El 502 de Cloudflare al enviar correos **NO es** rate limit de Gmail, **NO es** [OVERQUOTA], **NO es** imagen vieja y **NO es** pod caído/OOM.
Es **timeout del origen** causado por **descargas SÍNCRONAS y BLOQUEANTES de los adjuntos desde el Object Store** (`integrations.emergentagent.com/objstore`) dentro del request de envío. El Object Store está devolviendo **connect-timeout (8s), 500 y 503** para esos objetos, así que el request de envío se cuelga decenas de segundos/minutos y supera el timeout de origen de Cloudflare → "The origin web server returned an invalid or incomplete response".

- **PERO el event loop SÍ se bloquea** por llamadas `requests` síncronas (ver abajo) — eso no aparece como OOM, aparece como requests colgados.

### 3) Causa raíz del 502 al enviar correo — el request se cuelga en el Object Store
Trazas dominantes en el pod (todas hacia `integrations.emergentagent.com/objstore`, con `requests`/`urllib3` = cliente SÍNCRONO bloqueante):
```
requests.exceptions.ConnectTimeout: HTTPSConnectionPool(host='integrations.emergentagent.com', port=443):
  Max retries exceeded with url: /objstore/.../blindaje_adjuntos/194431449/CI_TITULAR.pdf
  (connect timeout=8)
requests.exceptions.HTTPError: 500 Server Error: .../blindaje_adjuntos/194431449/RESOLUCION.pdf
requests.exceptions.HTTPError: 500 Server Error: .../blindaje_adjuntos/194431449/JAVIERA_..._Deuda_Alimentos.pdf
WARNING:root:refetch_adjuntos ...: The read operation timed out
WARNING:root:refetch_adjuntos ...: cannot read from timed out object
WARNING:root:cloud_bunker manifiesto: 500 Server Error .../manifiesto.json
WARNING:root:cloud_bunker dashai: 503 Service Unavailable .../dashai/registros_dashai.json
ERROR:asyncio:Unclosed client session
```
Mecánica: el flujo de envío (adjuntar `blindaje_adjuntos`) hace **N descargas síncronas** al Object Store. Cada objeto agota 8s de connect-timeout y/o devuelve 500/503; con varios adjuntos por correo el request acumula decenas de segundos → **Cloudflare corta con "invalid or incomplete response"** antes de que el backend responda. El envío SMTP síncrono dentro del request agrava el tiempo total.

### 4) Hallazgo secundario (no es el 502, pero conviene corregir)
El digest se re-encola **cada ~60s** con:
```
INFO:root:📬 Resumen diario 8AM: {'success': False, 'error': 'PREVIEW OBLIGATORIO: este correo ya espera confirmación del Administrador'}
```
Es la propia regla de negocio ("preview obligatorio, espera confirmación del Admin") + un scheduler reintentando en bucle. No genera el 502, pero satura logs y reintenta indefinidamente.

## Qué NO se encontró
- Sin `smtplib`/SMTPException, sin timeout a `smtp.gmail.com`, sin `[OVERQUOTA]`, sin 535/534/550 de Gmail en la ventana (últimas 6h). El cuello de botella actual es el **Object Store**, no Gmail.

## Fix recomendado (código fuente — lo aplica E1 en preview y redeploya)
1. **Sacar la descarga de adjuntos y el envío SMTP del request** → moverlo a tarea de fondo / cola (`correos_salida_cola_blindada`) y que el endpoint responda 202 de inmediato. Así Cloudflare nunca espera al SMTP/objstore.
2. **Blindar `refetch_adjuntos` / descarga de `blindaje_adjuntos`**: timeout corto por objeto (p.ej. connect+read ≤ 5s), reintentos acotados con backoff, y **omitir el adjunto que falla** (enviar el correo sin él + log) en vez de dejar colgado el request. Nunca sumar N×8s dentro de un request web.
3. Reemplazar las llamadas **síncronas `requests`** del Object Store dentro del path async por cliente async (aiohttp) o `run_in_executor`, para no bloquear el event loop (esto conecta con el fix parcial anterior que redujo IMAP y desbloqueó Object Store — quedó fuera el path de adjuntos del envío).
4. Corregir el bucle del digest para no reintentar cada 60s cuando el estado es "PREVIEW OBLIGATORIO" (espera confirmación del Admin, no reintento).

## Dependencia upstream
El propio Object Store `integrations.emergentagent.com/objstore` está devolviendo 500/503/timeout para `central-mutuos/...` en este momento — es una condición del servicio de integraciones de Emergent. Aunque se blinde el código (recomendado), conviene reportar/verificar la salud de ese objstore, porque mientras devuelva 500/503 los adjuntos no se podrán recuperar.
