# RCA — Central Mutuos (risk-assess-17) · error Cloudflare "respuesta no analizable" ~16:55 UTC 31-ago

## Resumen ejecutivo
- El redeploy de hace ~1h **terminó OK y fue promovido** (run `741d1c2b`, redeploy, status=success, completado 16:07:29 UTC). El error del usuario **NO es el rollout** (ocurrió ~48 min después).
- El error de Cloudflare ("el origen devolvió una respuesta vacía / encabezados mal formados") es **intermitente** y coincide con **reinicios de los pods de backend disparados por fallo de liveness (HTTP 503)**.
- Causa raíz: el backend queda **con el event loop bloqueado** por una **avalancha de descargas objstore** (restauración BÚNKER de cientos de archivos) mientras el endpoint `integrations.emergentagent.com` **agota el tiempo de conexión (connect timeout=5s)**. Con `uvicorn --workers 1`, el worker no puede responder `/health` dentro de 1s → nginx devuelve 503 → kubelet mata el contenedor por liveness → reinicia → **la restauración masiva se ejecuta otra vez** → bucle. Durante cada reinicio el origen no responde y Cloudflare muestra el error.

### 4) RCA: ¿transitorio por rollout o problema real en la nueva imagen?
**Problema real en el comportamiento de runtime de la nueva imagen, NO el rollout.** Secuencia:
1. `integrations.emergentagent.com` (objstore) está inaccesible/lento → cada GET agota 5s de connect timeout.
2. El código dispara una **restauración/lectura masiva de objstore** (BÚNKER, cientos de objetos) de forma que **bloquea el único worker** (`--workers 1`).
3. `/health` no responde en 1s → nginx 503 → **liveness mata el pod** → reinicio.
4. Al reiniciar, **la restauración masiva se repite** → se re-abre el circuito → vuelve a bloquear → **bucle de reinicios** en ambas réplicas.
5. En cada ventana de reinicio el origen está caído/refusing → Cloudflare no obtiene respuesta válida → error "respuesta no analizable" para el usuario (~16:55 cae justo en la reterminación de `qq4j5` a las 16:50:45 con liveness 503 hasta 16:52:05).

El circuit breaker de 5 min **no es suficiente** porque (a) se reinicia el estado en cada restart del pod, y (b) el volumen de trabajo bloqueante antes de que se abra el circuito ya basta para tumbar liveness.

## Acciones recomendadas (código fuente — para E1)
Prioridad alta, en `backend/`:
1. **Sacar la restauración BÚNKER / fetch objstore del arranque y del event loop.** Que NO corra síncronamente en startup ni bloquee el worker: usar tarea de fondo con `run_in_executor`/thread pool o cola, con concurrencia acotada, y **perezoso/on-demand** en vez de restaurar cientos de objetos de golpe.
2. **Hacer el arranque resiliente al objstore caído**: no reintentar en avalancha; respetar el circuit breaker ANTES de encolar cientos de GETs; back-off exponencial; que un objstore inaccesible no impida servir `/api/*`.
3. **Desacoplar liveness de la disponibilidad del objstore.** Considerar un endpoint de salud liviano y aumentar `timeoutSeconds`/`failureThreshold` de la probe, o subir `--workers` (>1) para que la salud no dependa de un worker ocupado. (La probe nginx `/health` tiene timeout de 1s; un worker ocupado la reprueba.)
4. **Investigar por qué `integrations.emergentagent.com` da connect timeout desde el pod** (¿outage del objstore de Emergent, egress bloqueado, o URL/credencial objstore incorrecta tras el fix de "timeouts objstore"?). Si es outage de plataforma, es infra; si es config, corregir la config objstore.
