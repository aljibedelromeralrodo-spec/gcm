# RCA — risk-assess-17 redeploy failure (run e1f0e29c-4e1a-45f5-9806-47304df6b978)

## Verdict
Deploy failed at **deploy_k8s** because the backend **never completes application startup**, so the Kubernetes startup probe on `/health` returns **503** for the entire window and both pods are killed/restarted until the rollout times out ("deployment failed to become ready"). This is a **source-level / external-dependency fault**, NOT a manifest, image, or resource (OOM) problem. A blind redeploy of the same source will fail identically.

## Evidence
- **Pod events** (`get_pod_events`): both replicas show repeated `Warning Unhealthy: Startup probe failed: HTTP probe failed with statuscode: 503` (count 61–62 over ~5 min), then `Killing ... failed startup probe, will be restarted`. Container `last_termination = Completed, exit_code 0` (SIGTERM from the failed probe — NOT OOMKilled/137, NOT a crash).
- **Rollout log**: nginx logs a continuous stream of `connect() failed (111: Connection refused) while connecting to upstream ... "GET /health HTTP/1.1", upstream: "http://127.0.0.1:8001/health"` from 08:01 → 08:05. nginx (8080) is up; the FastAPI backend on **8001 is never accepting connections**.
- **App logs** (`fetch_app_logs`): uvicorn reaches `INFO: Started server process [24]` and `INFO: Waiting for application startup.` plus seeding messages (📧 Destinatarios, 👑 Gerencia Comercial, 🏛 Constitución, 📜 NORMATIVAS FIJAS) — but **never** logs `Application startup complete` and never starts serving on 8001.
- Interleaved throughout startup are **hundreds** of:
  `WARNING:root:objstore get clientes/.../<file>.pdf: 500 Server Error: Internal Server Error for url: https://integrations.emergentagent.com/objstore/api/v1/storage/objects/central-mutuos/clientes/...`
  Every objstore object fetch returns HTTP 500. These fire during the startup/lifespan phase (backend still not listening on 8001), i.e. they are **blocking boot**.

## Root cause
The FastAPI **startup/lifespan (and/or seeding) path performs a large volume of synchronous, blocking objstore fetches** against `integrations.emergentagent.com/objstore/.../central-mutuos/...`. That external endpoint is currently returning **500 for every object**, so each call is slow/failing. Because this work runs *inside* application startup, uvicorn never finishes startup, never binds `127.0.0.1:8001`, so nginx `/health` → 503 → K8s startup probe fails → pods killed/restarted → rollout timeout.

Contributing note: many object keys look mangled (e.g. `IVANA L.OPEZ`, `KANELA IBA_EZ`, `INSCRIPCIO_N`, `GRAVA_MENES`) — accent/space normalization issues that may also be contributing to the 500s, but the deploy-blocking problem is the **blocking-at-startup design**, not any single key.

Last healthy run e4af5d93 (Aug 26) used the same template/tier/image shape, so the regression is either (a) new startup code that eagerly iterates/fetches all client objects at boot, or (b) the objstore backend degrading to 500s while startup depends on it synchronously — most likely both.

## Fix (source — owned by E1, apply in the preview/source environment)
The app must be able to **boot without depending on objstore succeeding**. Options, in order of preference:
1. **Remove blocking objstore I/O from the startup/lifespan path.** Do not fetch client documents at boot. Make these fetches lazy (on first request) or move them to a background task that runs *after* the server is serving, so `Application startup complete` happens promptly.
2. If any seeding must run at startup, **wrap it so failures/timeouts never block startup** — catch exceptions, add short per-call timeouts, and cap/skip the bulk objstore enumeration entirely at boot.
3. Investigate why `integrations.emergentagent.com/objstore` returns 500 for these objects (mangled/URL-encoded keys with spaces & accents like `IBA_EZ`, `L.OPEZ`), and fix key normalization — but this is secondary; startup must not depend on it.

## Verification note
Not reproduced in the eph sandbox: the sandbox has no app secrets, no live DB, and cannot reach/authenticate the external objstore service, so this exact startup behavior can't be exercised there. Diagnosis is from the failing run's pod events, rollout log, and app logs (high confidence).

## Not the cause (ruled out)
- Not OOM/resource (exit 0, no 137, no OOMKilled; tier_2 unchanged).
- Not image pull (image pulled successfully on both nodes).
- Not a manifest/build fault (build succeeded; nginx & entrypoint behaving correctly — nginx is up and correctly proxying `/health` to 8001).
